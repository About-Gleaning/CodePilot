在确实需要用户决策后才能继续时，向用户发起结构化问题。

使用规则：
- 先自行读取上下文、检查代码和梳理约束；只有问题不能从现有信息推导，且继续猜测有风险时才使用。
- 单次最多提交 3 个问题；每个问题只承载一个决策点。
- 问题之间互不依赖时，优先放进同一次 `questions` 调用，减少来回打断。
- 后续问题严格依赖当前答案时，可以只问当前必须确认的问题。
- 选项必须是互斥且有实际差异的选择，不要提供明显无意义的选项。
- 如果推荐某个选项，把它放在第一位，并在 `label` 末尾添加 `(Recommended)`。

参数结构：
- `questions`：非空数组，最多 3 项。
- 每个问题必须包含 `id`、`question` 和 `options`。
- `id` 必须在本次调用内唯一，便于后续识别答案。
- `multiple` 默认 false；需要多选时设为 true。
- `custom` 默认 false；设为 true 时，系统会自动追加 `value="__custom__"`、`label="不是以上任何选项"` 的自由输入选项。
- 每个 `options` 项必须包含 `value` 和 `label`，且同一问题内 `value` 不能重复。
- 不要传入 `header`、`description` 等 schema 未定义字段。

适合场景：
- 需求范围存在多种合理解释。
- 实现方案存在用户可感知的取舍。
- 数据删除、权限、兼容性、外部成本等风险需要用户确认。

不适合场景：
- 问题能通过读取代码、配置、测试或文档得到答案。
- 只是低价值偏好，且合理默认值不会明显影响结果。
- 为了拖延实现而询问可以自行判断的问题。

示例：
```json
{
  "questions": [
    {
      "id": "implementation_scope",
      "question": "这次希望采用哪种实现范围？",
      "custom": true,
      "options": [
        {"value": "minimal", "label": "最小改动 (Recommended)"},
        {"value": "refactor", "label": "顺带重构"}
      ]
    }
  ]
}
```
